Errores Críticos
🔴 E01 · Regex sin flag multilinea para parseo de episodios ▶
server.js · línea ~389
// PROBLEMA: el contenido del script puede tener saltos de línea
const match = contents.match(/var episodes\s*=\s*(\[.*?\]);/i);
// . no captura \n por defecto → el match falla si hay datos multilínea

// CORRECCIÓN:
const match = contents.match(/var episodes\s*=\s*(\[[\s\S]*?\]);/i);

Si animeflv formatea el JS con saltos de línea (lo cual es común al minificar o prettificar), la regex no encuentra el array y devuelve 0 episodios sin lanzar error alguno.

🔴 E02 · CSS duplicado: .card y .card-img-wrapper definidos dos veces ▶

style.css define .card en línea ~241 (border-radius:12px, box-shadow básico) y de nuevo en línea ~1108 (border-radius:14px, box-shadow reforzado). La segunda regla sobreescribe a la primera, pero genera confusión de mantenimiento y 40+ líneas de CSS muerto.

🎨

Clases afectadas por duplicación

.card, .card-img-wrapper, .card-img-wrapper img, .card-img-wrapper img.loaded, .card:hover .card-img-wrapper img, .card-title → todos duplicados con valores ligeramente distintos.

🔴 E03 · CORS abierto sin restricción de origen ▶
server.js · línea 41
app.use(cors());  // Permite * → cualquier origen puede consultar el API

// Corrección:
app.use(cors({ origin: ['https://tudominio.com', 'http://localhost:3000'] }));

Cualquier sitio externo puede hacer peticiones a tu API y usar tu scraper como proxy gratuito, agotando tu cuota de IP en animeflv.

🔴 E04 · Cache del servidor sin límite de tamaño — Memory Leak ▶

El Map de cache nunca purga entradas antiguas excepto cuando se accede a la key específica y el TTL expiró. Con miles de anime distintos, el cache crece indefinidamente en RAM hasta que el proceso muera o el servidor se reinicie. No hay LRU, no hay límite máximo de entradas.

Solución mínima
// Agregar límite de 1000 entradas con LRU manual:
const MAX_CACHE = 1000;
const cacheSet = (key, data) => {
  if (cache.size >= MAX_CACHE) {
    const firstKey = cache.keys().next().value;
    cache.delete(firstKey);
  }
  cache.set(key, { data, timestamp: Date.now() });
};

🔴 E06 · Sin rate limiting en endpoints del API ▶

Ningún endpoint tiene rate limiting. Un bot puede hacer 10,000 peticiones/segundo a /api/latest, generando miles de requests a animeflv desde la misma IP del servidor, resultando en bloqueo de IP. Se recomienda express-rate-limit con límite de 30-60 req/min por IP.

🔴 E08 · overflow:hidden en body corta el acceso táctil en iOS Safari ▶

style.css línea 38 tiene overflow: hidden en body. En iOS Safari esto bloquea el scroll nativo del momentum y genera comportamientos inesperados al abrir overlays con contenido scrollable. El scroll interno funciona gracias a -webkit-overflow-scrolling: touch en .content-scrollable, pero es frágil.

Sugerencias Propuestas
4 propuestas de mejora proactivas sugeridas por knoX basadas en el análisis del proyecto — más allá de los bugs existentes.
Propuesta 1 — Sistema de Fallback Multi-Proveedor
Resiliencia · Esfuerzo: 3 días

Abstracción de fuentes de datos con adaptadores

Actualmente, toda la lógica de scraping apunta exclusivamente a www3.animeflv.net. Si el dominio cambia, la app queda completamente inoperativa. knoX propone crear una capa de abstracción con múltiples adaptadores:

Arquitectura sugerida
// providers/animeflv.js
module.exports = { getLatest, getTrending, getGenre, getInfo, getVideo }

// providers/backup-provider.js (jkanime, monoschinos, etc)
module.exports = { getLatest, getTrending, ... }

// services/anime-service.js
const providers = [animeflv, backupProvider];
async function withFallback(method, ...args) {
  for (const p of providers) {
    try { return await p[method](...args); } 
    catch { continue; }
  }
  throw new Error('Todos los proveedores fallaron');
}
Propuesta 2 — Service Worker para modo Offline
PWA · Esfuerzo: 2 días

Cache de assets y datos via Service Worker

La app ya tiene manifest.json referenciado y está pensada como PWA móvil. Añadir un Service Worker que cachée los assets estáticos (HTML, CSS, JS, fonts) y las respuestas de la API de info de animes ya visitados permitiría navegación offline de la biblioteca.

Cache Shell

App Shell Strategy

Cachear index.html, style.css, script.js en install. Servir desde cache en fetch si sin red.

Runtime Cache

Stale-While-Revalidate

Para /api/info/* y /api/trending: servir el cache inmediatamente mientras se actualiza en background.

Data Flow
Flujo de Información
Cómo se procesa la información desde la solicitud del usuario hasta el renderizado en pantalla, pasando por el backend y el scraping.
Flujo: Usuario abre un anime → Ve el episodio
Paso 1 · Usuario
Click en card de anime en el home
UIBuilder.buildCard() registra un event listener en el click del card. Se invoca DetailOverlay.open(animeId).
Paso 2 · Frontend
API.getInfo(id) → fetch /api/info/{id}
El cliente verifica pendingRequests (¿ya hay una petición en vuelo?) y requestCache (¿tenemos datos frescos?). Si no, lanza fetch real al servidor.
Paso 3 · Servidor
Cache check → Axios a animeflv
El servidor revisa su Map de cache con TTL de 60 min para info. Si miss, hace GET a https://www3.animeflv.net/anime/{id} con headers spoofed (User-Agent de Chrome).
Paso 4 · Scraping
Cheerio parsea el HTML de animeflv
Extrae: título (7 selectores en cascada), cover (3 estrategias), géneros (.Nvgnrs a), sinopsis (.Description p), estado (.AnmStts span), episodios (regex sobre script inline var episodes=[...]).
Paso 5 · Respuesta
JSON normalizado → Cliente → Render
El servidor normaliza y cachea la respuesta. El cliente la recibe, actualiza AppState.currentAnime, llama Recommendations.updateWeights(genres), y renderiza el overlay de detalle.
Paso 6 · Episodio
PlayerOverlay.open(epNumber)
Llama API.getVideo(id, epNumber) → /api/video/{id}/{cap} → Axios a /ver/{id}-{cap} → Regex busca var videos={...} → extrae array SUB → mapea URLs de servidores → retorna al cliente → iframe carga el primer servidor.

Medidas Actuales — Evaluación
✓ Bien hecho

Helmet.js activo

Se aplican headers de seguridad HTTP: X-Frame-Options, X-Content-Type-Options, Referrer-Policy. ContentSecurityPolicy desactivado deliberadamente (necesario para iframes de video externos).

✓ Bien hecho

Validación de parámetros de entrada

validatePage() y validateGenre() sanitizan input numérico y de texto. cleanId y cleanCap limitan longitud y carácteres. Previene inyecciones básicas en las rutas de axios.

✓ Bien hecho

Retry con backoff exponencial

retryRequest() usa exponential backoff con cap de 5 segundos. Previene thundering herd si animeflv responde lento.

✗ Faltante

Sin autenticación en el API

Cualquier persona que conozca la URL del servidor puede usar el API sin restricción. Considerar API key o JWT si se despliega públicamente.

ℹ️

Nota sobre legalidad del scraping

El scraping de animeflv puede violar sus Términos de Servicio. El uso de User-Agent spoofing (simulación de Chrome) para acceder programáticamente es una práctica que muchos sitios prohíben explícitamente en sus ToS. Consultar asesoría legal antes de desplegar en producción pública.

Fase 3 — Producción (Mes 3+)
Infrastructure

Redis como cache distribuido

Reemplazar el Map in-memory por Redis. Permite múltiples instancias del servidor (horizontal scaling) sin duplicar requests a animeflv. TTL nativo. Persistencia opcional.

Testing

Suite de tests (Jest + Supertest)

Tests unitarios para normalizeAnime(), normalizeEpisode(), cacheGet/Set, validatePage(), validateGenre(). Tests de integración para los endpoints del API. Coverage objetivo: 70%+.

Monitoring

Dashboard de salud + alertas

Panel /admin con métricas en tiempo real. Alertas si animeflv devuelve 403 o timeout. Notificación si cache size supera límites. Log estructurado (JSON) para análisis.

Containerization

Docker + CI/CD

Dockerfile con Node.js LTS Alpine. docker-compose con Redis. GitHub Actions para lint → test → build → deploy automático en cada push a main.

Conclusión knoX

AnimeSAO Pro es un proyecto con buenas bases visuales y una arquitectura modular coherente. El mayor riesgo inmediato es el endpoint de género faltante y las vulnerabilidades de seguridad (CORS abierto, sin rate limit). Con las correcciones de Fase 0 aplicadas, el producto sería estable y seguro para un despliegue real. La hoja de ruta propuesta llevará el proyecto de MVP a producción robusta en ~3 meses de trabajo sostenido.
